# Beekeeper of Ukraine — інтернет-магазин

Магазин продуктів бджільництва: мультимагазинні ціни й залишки, ролі (адмін/продавець/автор/покупець),
акції та промокоди, перевірка дипломів, редагований контент, PWA-адмінка з мобільного, сповіщення
Telegram / Email / Web Push, автоматичне SEO (sitemap, JSON-LD, OG-теги).

Чистий PHP 8.1+ без залежностей — працює на XAMPP і на shared-хостингу HostIQ простим копіюванням.

## Запуск на ПК (XAMPP + Docker)

1. **Запустіть XAMPP** (Apache).
2. **Запустіть базу** — у папці `C:\xampp\htdocs\bofu` виконайте в командному рядку:
   ```
   docker compose up -d
   ```
   Перший запуск завантажить MySQL (~1 хв). База слухає порт **3307**, дані зберігаються у Docker-томі.
3. Відкрийте **http://localhost/bofu/** — при першому відкритті сайт сам створить таблиці й демо-дані.

**Демо-вхід:** кнопка «Увійти» → «Увійти як адміністратор / продавець / покупець».

phpMyAdmin для бази: **http://localhost:8081** (bofu / bofu_secret).

## Структура

```
index.php          — точка входу (весь трафік через неї)
config.php         — конфігурація за замовчуванням (не редагувати)
config.local.php   — ваші локальні перевизначення (створіть за потреби)
app/Core           — ядро: роутер, БД, шаблони, авторизація, сповіщення, WebPush
app/Controllers    — логіка сторінок (вітрина + адмінка)
app/Views          — шаблони
assets/            — стилі, шрифти, зображення, завантажені фото (uploads/)
bin/cli.php        — консольні команди: migrate | seed | fresh
storage/           — логи, сесії (не публікується)
```

## Замовлення з кількох магазинів

Одне замовлення покупця автоматично розкладається на **підзамовлення** — по одному на магазин,
який реально виконує позиції. Так один продавець не бачить чужої роботи, а покупець має одне
замовлення з одним номером.

```
BOFU-260801-A3F2       головне: контакти, доставка, промокод, сума, зведений статус
├── BOFU-260801-A3F2/1  Магазин №1 — свої позиції, свій статус, свій продавець
└── BOFU-260801-A3F2/2  Магазин №2 — …
```

- **Хто виконує позицію** визначається при оформленні: самовивіз — обраний магазин; інакше той,
  де вистачає залишку на всю кількість (далі — де хоч щось є, і як запасний — магазин за
  замовчуванням, для товарів «під замовлення»). Залишки списуються саме з нього.
- **Підзамовлення створюється завжди**, навіть коли магазин один. Тоді передача позиції іншому
  магазину нічого не перебудовує, а доступи, сповіщення й статуси працюють одним шляхом.
- **Статус головного рахується сам**: він дорівнює найменш просунутій частині. Щойно всі магазини
  поставили «Доставлено» — головне стає «Доставлено» без ручних дій. Усі скасовані → скасовано.
  Адмін може проставити статус усім частинам одразу з картки головного замовлення.
- **Передача позиції в інший магазин** (адмінка → Замовлення → кнопка «→» біля позиції): позиція
  переїжджає в підзамовлення того магазину (створюється, якщо його ще не було), залишок повертається
  старому магазину й списується в нового, новий продавець отримує сповіщення. **Ціна не змінюється** —
  покупець платить рівно те, що бачив у кошику. Підзамовлення, що лишилось без позицій, закривається.
- **Скасування повертає товар на склад** — рівно те, що з точки колись зняли (позицію могли
  замовити понад залишок, і повертати «всю кількість» означало б подарувати магазину неіснуючий
  товар). Якщо на цей товар хтось чекав — йому одразу йде «зʼявився в наявності». Зняття
  скасування забирає товар назад і чесно пише в історію, якщо його вже розібрали.
- **Продавець** бачить у списку лише свої частини, але може відкрити замовлення цілком: контакти,
  доставку й те, які магазини ведуть решту частин (без права їх змінювати).
- **Покупець теж отримує сповіщення** (подія «Покупцю: рух його замовлення»): при оформленні й на
  кожній зміні статусу. Коли рухається одна частина розділеного замовлення — у повідомленні названо
  магазин і перелічено саме його товари, щоб «В дорозі» не читалось як «усе замовлення виїхало».
  Зареєстрованому — тими каналами, які він лишив собі в кабінеті, гостю — на пошту із замовлення.
- **Магазин за замовчуванням** (Налаштування → Замовлення) — точка, якій дістаються позиції, яких
  немає ніде. Без вибору їх забирає перша активна точка, і це залежить від порядку сортування
  магазинів, тож краще вказати явно.
- Уся історія — розділення, зміни статусів, передачі — пишеться в `order_events` і показується
  на сторінці замовлення.

Технічно: обидва рівні лежать в одній таблиці `orders` (`parent_id` = головне, `seq` = номер частини),
позиції `order_items` — **тільки** в підзамовленнях. Логіка зібрана в `app/Core/OrderFlow.php`.

## Каса: продаж за покупця (адмінка → Каса)

Продавець набирає замовлення сам: покупець подзвонив або прийшов у точку. Сторінка
`/admin/orders/new`, право `orders.create` (у ролі «Продавець» є за замовчуванням).
Замовлення виходить звичайним: той самий номер, підзамовлення магазину, списання залишків,
історія й сповіщення. У рядку лишається `source` (`site` | `phone` | `offline`) і
`created_by_user_id` — хто саме його завів.

**Три кроки: покупець → товари → отримання.** Продаж — послідовна розмова («хто ви» →
«що берете» → «як віддаємо»), і екран іде тим самим порядком. Спершу все було на одному
екрані, і воно там уміщалось, але дивитись доводилось усюди одразу: телефон покупця, плитка,
доставка й кнопка оформлення в різних кутах.

Кроки перемикаються **в браузері**, а не запитами: чек живе в сесії, і бігати за ним на
сервер щоразу, коли натиснули «Далі», нема потреби. Форма лишається **одна на всі три
кроки** — оформлення відправляє все разом, тож поля попередніх кроків нікуди не діваються.

Над кроками — стрічка з підсумками: кого записали, скільки позицій і на яку суму, як
віддаємо. Повертатись, щоб пригадати, не треба; клацнути можна на будь-який крок.
Єдина заборона — перейти до отримання з порожнім чеком: оформити його все одно не вийде,
і дізнатись про це краще одразу, а не після заповнення доставки.

Крок памʼятається при перезавантаженні. Їх за продаж два: зміна точки (у неї свій цінник,
тож плитка й чек перераховуються) і повернення з помилкою оформлення — воно завжди веде на
третій крок, бо саме там кнопка, з якої помилку отримали.

Швидкість набору не постраждала: сканер, пошук і плитка живуть на другому кроці разом.
Три способи покласти позицію, усі три працюють одночасно:

- **плитка товарів** — тап = +1. На кількох десятках позицій це швидше за будь-який пошук,
  і саме так влаштовані каси в невеликих магазинах;
- **сканер** — поле вгорі. Сканер працює як клавіатура: набирає код і тисне Enter, тож
  окремого «драйвера» не треба. Тримайте курсор у полі — і більше нічого робити не треба;
- **вітрина** — кнопка «Вийти на сайт». Унизу зʼявляється смужка продажу, і кнопки «У кошик»
  на сайті додають товар у цей самий чек. Це для випадку, коли покупцеві треба показати
  картку товару з фото й описом.

Чеком служить **звичайний кошик сайту** — той самий, у який кладуть покупці. Так працює все,
що вже написано: ліміти залишку, варіанти, ціни магазину, кнопки «У кошик». Власний кошик
продавця відкладається на час продажу й повертається, коли чек оформлено або скасовано:
чужа покупка не стирає те, що людина відклала собі. Живе чек у сесії — один продавець веде
один чек за раз (відкладені чеки — це вже чернетки в базі, і робити їх варто тоді, коли
зʼявиться жива черга).

**Покупець — поле чека, а не вхідні двері.** Номер вписують будь-коли: на початку, посеред
набору чи перед самим оформленням. Кнопка «Знайти» показує, кого знайшли і скільки в нього
замовлень, — продавець має бачити, що причепив саме ту людину.

**Чий це покупець — вирішує номер телефону** (`app/Core/Customers.php`):

- **номер є, акаунт знайдено** — замовлення лягає в історію цієї людини;
- **номер є, акаунта немає** — акаунт створюється (роль «покупець», службова пошта
  `…@offline.local`). Далі людина входить на сайт цим самим номером і бачить свою покупку;
- **номера немає** — замовлення анонімне (`user_id` порожній, `phone` — порожній рядок).

Номер склеює записи так само, як при вході через месенджер: він єдине стале імʼя покупця,
за ним же рахуються ліміти промокодів. Тому окремого «гостьового» акаунта тут немає —
він розірвав би історію покупок навпіл.

**Анонімно можна лише те, що анонімним і буває**: видача з рук у точці. Дзвінок без номера
не приймається (нічим підтвердити замовлення й нікому передзвонити), доставка — теж
(посилку нікому вручити). Це єдине обмеження форми; решта полів необовʼязкові.

Галка «Товар віддано покупцю» закриває замовлення тим самим рухом: статус одразу
«Доставлено», а сповіщення «нове замовлення» магазину не йде — його щойно зробив той,
хто його й виконав. Знята галка лишає замовлення в роботі (відклали до завтра).

Ціни беруться за магазином-продавцем, разом із його акціями; зміна магазину перемальовує
і плитку, і чек — другої, javascript-ної копії ціноутворення навмисно немає. Промокод
перевіряється тими самими правилами, що й у кошику.

## Коди й штрихкоди (адмінка → Каталог)

Два різні поля, і це не дублювання:

- **артикул** (`sku`) — ваш внутрішній код для обліку, придумуєте ви: «MED-LIP-05»;
- **штрихкод** (`barcode`) — те, що надруковано на етикетці й читає сканер: EAN-13.

В одному полі вони рано чи пізно перетруть одне одного, тому їх два. У товару з фасовками
коди належать **фасовці**: етикетку клеять на банку, а не на «мед узагалі», і скан має
потрапити в конкретну позицію.

Заповнюють їх на окремому екрані **Каталог → Коди й штрихкоди**. Він заточений під одну роботу:
пройтись товарами з річчю в руках і проставити коди, тож угорі **фільтр** — пошук (назва,
артикул, код), категорія й готові добірки:

| Добірка | Навіщо |
|---|---|
| **Без штрихкоду** | кому ще не проставлено — головна добірка, з нею й ходять |
| **Зі штрихкодом** | перевірити вже зроблене |
| **З помилкою** | збита контрольна цифра або однаковий код у двох позицій |
| **Свої коди** | ті, що створені тут, — їх треба надрукувати й наклеїти |

Три способи заповнити, бо в житті трапляються всі три:

- **фабрична етикетка є** — USB-сканер (станьте в поле й піднесіть) або **📷** просто в рядку:
  камера читає код і кладе його в це поле;
- **етикетки немає** (своя банка меду) — **✨** у рядку: створює власний код **для цієї однієї
  позиції**. Масової кнопки «заповнити все» немає навмисно: коди проставляють по одному, разом
  із наклеюванням, і «створити 200 кодів одним кліком» лише плодить те, чого ніхто не надрукує;
- **код відомий із накладної** — ввести руками.

**Свої коди впізнаються з першого погляду**: вони починаються з `200` і позначені міткою
«свій код». Діапазон 20–29 стандарт GS1 лишив магазинам для внутрішнього вжитку, тож такий код
гарантовано не збігається з жодним чужим товаром у світі. Код виводиться з номера позиції
(`Barcode::make`), тому повторне натискання дає той самий код, а не новий.

**🖨 у рядку** відкриває наліпки на друк — 6/12/24/48 копій на аркуші, з назвою позиції над
кожним кодом. Друкується збережений код: малюнок креслить сервер (`Barcode::svg()`), і другої
копії цього креслення в браузері немає навмисно.

**Описка ловиться одразу.** Остання цифра штрихкоду рахується з попередніх — саме щоб її було
видно. Код зі збитою цифрою підсвічується, поруч пишеться, яким він має бути, і є кнопка
«виправити». Так само підсвічуються однакові коди: інакше каса щоразу братиме той товар, який
трапиться першим, і продавець цього не помітить.

Код, записаний на **товарі з кількома фасовками**, не спрацює ніколи — сканер не знатиме, яку
фасовку класти в чек. Такий код показується з поясненням і кнопкою «перенести в першу фасовку».
Якщо ж фасовка одна, код товару працює: одна фасовка — це не вибір (так само поводиться й кошик
на вітрині).

Каса шукає в такому порядку: штрихкод фасовки → штрихкод товару → артикул фасовки → артикул
товару. Збіг **тільки точний**: «схожий» код означав би чужий товар у чеку. Поки жоден код не
заповнений, каса каже про це просто на екрані сканера — інакше сканер виглядав би зламаним.

### Чим сканувати

- **USB-сканер** — нічого налаштовувати не треба: для компʼютера він звичайна клавіатура.
  Тримайте курсор у полі сканера, підносьте до етикетки — позиція лягає в чек сама.
- **Камера** — кнопка «📷 Камера» на касі. На Android працює вбудований у браузер
  `BarcodeDetector`, а де його немає (на Windows — ніде) вмикається власний декодер
  `assets/js/barcode.js`: EAN-13 і EAN-8, кілька смуг кадру, обидва напрямки.
  Камеру браузер дає лише на `https://` (або `localhost`) — по локальній http-адресі
  з телефона вона не увімкнеться, і каса про це скаже.

Прочитаний код завжди перевіряється **контрольною цифрою**: вигаданий код у чеку гірший за
непрочитаний — чужий товар ляже туди тихо. Декодер живе в браузері, тож і перевіряється в
браузері: відкрийте `tests/barcode.html` (генерує штрихкоди, крутить їх, зашумлює й читає).

## Вхід через месенджер

Вхід через Telegram / Viber завершується **лише після того, як людина поділиться номером
телефону** — кнопкою в самому боті (`request_contact` у Telegram, `share-phone` у Viber).
До цього моменту токен входу лишається непідтвердженим, а акаунт не створюється.

Контакт просимо **щоразу**, навіть коли номер в акаунті вже записаний: записаний номер
нічого не доводить, його міг вписати хто завгодно з клавіатури. Володіння підтверджує
лише контакт, надісланий самим месенджером. Один `chat_id` завжди належить одному акаунту —
коли номер приводить до іншого запису, стара прив'язка знімається.

Номер приводиться до єдиного вигляду однією функцією на весь сайт — `AuthTokens::normPhoneAny()`.
Український код країни має **сталу довжину**: `380` і рівно 9 цифр. Зайва цифра (`+38063463513278`)
відхиляється, а не проходить як «закордонний номер»: коду країни `380X` не існує ні в кого, тож це
завжди описка — і без цього правила замовлення поїхало б на номер, якого немає, а помітилось би це
аж при дзвінку. `AuthTokens::phoneProblem()` пояснює людині, що саме не так, замість одного
«неправильний номер» на всі випадки.

**Дублікати неможливі структурно**: на `users.phone` стоїть UNIQUE-індекс. Перевірки в коді
(`Profile`, `Users::readPhone`, `BotAuth`) лишаються — вони дають людині зрозуміле пояснення, —
але навіть новий шлях, який їх омине, не заведе другого акаунта на той самий номер. `NULL`
дозволений скільки завгодно: акаунт без номера просто не пройде далі профілю.

Причин дві. Телефон обовʼязковий (гейт у `App::run()` не пускає далі профілю), тож без нього
людина входила і одразу впиралась у форму. І головне: покупець, який колись замовляв за
номером, отримував **другий** акаунт — замовлення лишались у першому. Тепер номер склеює
записи: `BotAuth::resolveUser()` шукає спершу за телефоном і лише потім за id месенджера.

У Telegram обовʼязково звіряється `contact.user_id` з `from.id`: переслати чужий контакт із
адресної книги можна, і без цієї перевірки чужим номером можна було б увійти в чужий акаунт.
У Viber перевірка не потрібна — `share-phone` віддає номер самого співрозмовника.

Тексти всіх кроків бота редагує адмін (Налаштування → «Тексти бота при вході»), порожнє поле
повертає типовий. Після входу бот шле кнопку-посилання назад на сайт — адресу візьміть із поля
«Адреса сайту для кнопки в боті»: Viber стукає у webhook власним запитом, і визначити її з
контексту не завжди можливо.

## Налаштування інтеграцій (адмінка → Налаштування)

- **Google OAuth**: Google Cloud Console → Credentials → OAuth Client ID (Web).
  Redirect URI показано на сторінці налаштувань. Поки ключів немає — працює демо-вхід.
- **Telegram**: створіть бота у @BotFather → вставте токен. Кожному продавцю/адміну впишіть
  його Chat ID (адмінка → Користувачі). Сповіщення про нові замовлення прийдуть у Telegram.
- **Нова Пошта**: API-ключ з кабінету novaposhta.ua → автопідказки міст і відділень у checkout
  і створення накладних просто із замовлення. Див. окремий розділ «Нова Пошта» нижче.
- **Google Maps**: ключ для карти точок продажу — див. окремий розділ «Карта точок продажу»
  нижче. Без ключа сайт працює як працював: замість карти адреса з кнопкою маршруту.
- **Web Push**: ключі генеруються автоматично; на телефоні запрацює після переносу на HTTPS.
  Якщо на Windows ключі не створюються — openssl не знаходить `openssl.cnf`; вкажіть його
  у змінній `OPENSSL_CONF` (`C:\xampp\apache\conf\openssl.cnf`).
- **Кнопка «Перевірити зʼєднання»** (там же, у Налаштуваннях) питає Telegram, Viber і Нову Пошту
  тим, що зараз у полях, **нічого не зберігаючи**. Виклики лише читальні: webhook не переставляє,
  листів і повідомлень не шле. Показує, зокрема, **куди вказує webhook Viber-бота** — у бота він
  лише один, тож якщо там чужа адреса, збереження токена забере бота з того сайту.
- **Розсилка** (адмінка → Розсилка): адреси збираються лише за явною галкою згоди — при оформленні
  замовлення або в профілі. Експорт CSV містить колонку `unsubscribe_url` — це персональне посилання
  на відписку, яке **обовʼязково** треба вставляти в кожен лист розсилки.
- **Демо-вхід вимкнений за замовчуванням** (він дає адмін-права одним кліком без пароля).
  Щоб увімкнути його *локально*, поки не налаштовано Google/Telegram, — у `config.local.php`:
  ```php
  <?php return ['demo_login' => true];
  ```
  На бойовому сервері не вмикайте: цей рядок = відкрита адмінка для будь-кого.

## Нова Пошта: накладні й відстеження

Замовлення проходить шлях від «покупець обрав відділення» до «посилку отримано» без жодного
переписування номерів руками: накладна створюється кнопкою в картці замовлення, а її статус
далі оновлюється сам і доходить до покупця в кабінет.

### Що налаштувати (один раз)

1. **API-ключ** — кабінет novaposhta.ua → Налаштування → Безпека. Вставити в адмінці →
   Налаштування → «Інтеграції та SEO». Ключ безкоштовний.
2. **Відправник** — там же, картка «Нова Пошта: відправник». Натисніть «Підтягнути з Нової
   Пошти»: контрагента й контактну особу беремо з вашого кабінету, вигадати їх не можна —
   накладна створюється саме від їхнього імені. Далі місто й відділення відправлення.
3. **Типова накладна** — вага, опис вантажу, хто платить за доставку, чи ставити післяплату
   за замовчуванням. Це лише передзаповнення форми: продавець може змінити будь-що перед
   створенням.
4. **Кнопка «Перевірити зʼєднання»** покаже окремим рядком «НП: відправник» — чи вистачає
   даних, щоб накладна взагалі створилась.

**Магазин може відправляти зі свого відділення** (Магазини → рядок точки → «Відправлення
Новою Поштою»). Порожньо — їде зі спільного. Контрагента там немає навмисно: він належить
кабінету НП, а кабінет (тобто ключ) у сайту один на всі точки.

**Вага береться з товарів** (Каталог → товар → «Вага, кг»; у товару з фасовками — у самій
фасовці). Форма накладної рахує вагу × кількість по всіх позиціях, а де ваги немає — бере
типову з налаштувань. За вагою НП рахує гроші, тож проставити її варто.

### Накладна на кожну частину замовлення

Розділене між магазинами замовлення дістає **стільки накладних, скільки магазинів його
виконують**. Це не ускладнення заради ускладнення: дві коробки з різних міст фізично не
можуть їхати під одним номером. Покупець бачить список номерів із назвою магазину біля
кожного, а продавець — лише свою частину.

Створення (адмінка → Замовлення → картка → блок під позиціями):

- **«Створити накладну»** — звичайний шлях. Вага, місця, оцінка, післяплата, платник —
  усе передзаповнене, лишається звірити. Після створення: частина переходить у «В дорозі»,
  покупцю йде номер із посиланням на відстеження.
- **«Вписати номер»** — для накладних, оформлених у кабінеті чи застосунку НП або просто на
  відділенні. Це не «запасний варіант на випадок поломки», а звичайний шлях: далі все працює
  однаково, трекінгу потрібен лише номер. Вписаний номер одразу перевіряється в НП.
- **«✕ Накладна»** — відкріпити. Скасувати накладну в НП вдається, лише поки посилку не
  прийняли у відділенні; якщо вже прийняли, номер відкріпиться тут, а посилка їхатиме далі —
  про це буде сказано прямо.

**Куди везти, береться із замовлення** — форма створення накладної адресу не питає: покупець
обрав її сам. Але саму доставку в картці змінити можна, і це окрема дія: блок «Доставка»
праворуч → «**Змінити доставку**». Там перемикається **спосіб** (Нова Пошта ↔ Самовивіз ↔
Інше) і все, що йому належить: відділення чи вулиця для пошти, точка видачі для самовивозу,
довільний опис для «іншого». Це для випадків, коли покупець передумав або домовились
телефоном, — інакше довелося б перестворювати замовлення, втрачаючи його номер і історію.

Три речі, які варто знати про цю форму:

- **зміна стосується всього замовлення** — усі магазини везуть в одне місце. Точка видачі
  при самовивозі ставиться головному замовленню й не чіпає того, який магазин що виконує;
- **покупцю повідомлення не йде**: він або сам попросив, або ви щойно з ним говорили;
- **поки виписана накладна, доставка не змінюється** — спершу відкріпіть її. Інакше посилка
  поїхала б туди, куди її вже відправили.

Окремий випадок — адреса, записана **текстом, без звʼязку з довідником** (старе замовлення
або людина вписала відділення руками, не торкнувшись підказки). Накладну за нею не створити:
НП приймає посилання, а «Відділення №5» у місті буває не одне. Тоді та сама форма відкрита
одразу й названа «⚠️ Уточнити відділення для накладної» — оберіть зі списку, покупцю робити
нічого не треба.

**Курʼєрська доставка** працює нарівні з відділенням: покупець обирає «Курʼєром на адресу»
в checkout, вулиця береться з довідника НП, і накладна створюється з тими самими кнопками.

### Відстеження

Статуси тягне команда, яку ставлять у cron **раз на годину**:

```
0 * * * * php /home/USER/site/bin/cli.php np:track
```

За прохід питає до 100 накладних (стільки НП приймає за запит), першими — ті, кого
перевіряли найдавніше. Отримані й видалені не питає ніколи: їхній стан уже не зміниться,
а ліміт запитів у НП спільний на весь сайт. У картці замовлення є кнопка **«↻ Статус»** —
для випадку «покупець дзвонить просто зараз і питає».

Що з цього виходить само:

- посилка поїхала або прибула у відділення → частина стає «В дорозі»;
- посилку отримано → частина стає «Доставлено», а коли всі частини закриті — і все замовлення;
- статус **не відкочується назад**: продавець міг поставити «Доставлено» руками (покупець
  забрав у точці), і скасовувати його рішення через те, що НП ще не оновилась, не можна.

**Покупцю пишемо тричі, не частіше**: коли є номер, коли посилка чекає у відділенні й коли її
отримано. «Виїхала з сортувального центру» він подивиться в застосунку НП, якщо схоче; від нас
це було б спамом. Подія називається «Покупцю: накладна й рух посилки» — її, як і решту, можна
вимкнути в Налаштуваннях сповіщень, а покупець вимикає собі сам у кабінеті.

**Де це видно.** Покупцю — у кабінеті (`/orders`): номер із кнопкою «Копіювати», статус,
орієнтовна дата, сума післяплати. Гостю — на сторінці підтвердження замовлення за тим самим
посиланням, що він отримав при оформленні: кабінету в нього немає, і це його єдине вікно.
Продавцю — у списку замовлень під статусом, плюс фільтр: **без накладної** (те, що треба
зібрати й відправити — головна добірка на початок дня), **у дорозі**, **чекає у відділенні**
(покупець не забирає — час подзвонити), **проблема**.

### Права

Створювати накладні дозволяє окреме право **«Створювати накладні Нової Пошти»** (`orders.ship`,
у ролі «Продавець» є за замовчуванням). Дивитись і вести замовлення можна й без нього: накладна
коштує грошей і створюється від імені магазину, тож це не додаток до «змінювати статус».
Продавець керує накладними **лише своїх** частин, адміністратор — усіма.

## Безпека

- Ціни, знижки й підсумок рахуються **тільки на сервері** з БД. З браузера приймаються лише
  `product_id`, `variant_id`, `qty` — підмінити ціну через POST або DevTools неможливо.
- **Ролі.** Адмін веде сайт цілком. Продавцю доступні лише замовлення його магазинів та
  **ціни й залишки цих магазинів**; картку товару (назва, опис, базова ціна, варіанти, фото),
  медіа-бібліотеку, налаштування, користувачів, акції та контент змінює лише адмін.
  Перевірка — на сервері (`Products::save()`, `Auth::requireAdmin()`), форма її лише повторює.
- **Доступ до точки закінчується разом із роллю.** Прив'язка людини до магазину
  (`seller_stores`) існує лише поки в неї є роль продавця: знімають роль — вона зникає з усіх
  точок, і повернення ролі доступу **не відновлює**, магазини треба призначити наново
  (`Users::saveStores()`). Інакше рядок прив'язки пережив би звільнення й одна галка,
  повернена через рік зовсім для іншої точки, мовчки відкрила б старі залишки й замовлення.
- **Файли поза доступом ззовні**: `app/`, `bin/`, `storage/` (сесії, логи, SQLite) і `config*.php`
  закриті власними `.htaccess` — вони працюють навіть якщо `mod_rewrite` вимкнений.
  У `assets/uploads/` заборонено віддавати скрипти; фото ще й перекодовуються через GD.
- Дані, що потрапляють усередину `<script>` (JSON-LD, варіанти товару), виводяться через
  `json_js()` — назва товару з `</script>` не може розірвати тег.
- Обовʼязковий телефон: номер нормалізується до `+380XXXXXXXXX` (або E.164), сміття не проходить.
  Правило одне на весь сайт (форми, вхід за номером, гейт) — `AuthTokens::normPhoneAny`,
  зафіксоване тестом
  `tests/phone.php`. У браузері воно продубльоване (`assets/js/app.js`), щоб людина бачила
  помилку одразу, а не після перезавантаження сторінки: **міняючи одне, міняйте й друге** —
  розʼїзд цих двох місць виглядає як «форма не приймає правильний номер».
- Сторінка «замовлення прийнято» відкривається за випадковим токеном, а не за номером замовлення.
- Обмеження частоти (таблиця `rate_hits`, за IP): оформлення 15/год, вхід через месенджер 20/год,
  код на телефон 10/год, довідник Нової Пошти 300/год, перевірка диплома 40/год. У формі checkout
  є honeypot-поле для ботів.
- **За Cloudflare або балансувальником** увімкніть у `config.local.php` `'trust_proxy' => true`,
  інакше всі відвідувачі рахуватимуться як один IP. Без проксі лишайте `false` — інакше ліміт
  обходиться підробкою заголовка `X-Forwarded-For`.
- **Заголовки безпеки** (`Core/Security.php`, шлються найпершими в `App::run()`): `nosniff`,
  `X-Frame-Options: DENY`, `Referrer-Policy`, `Permissions-Policy` (з камери — лише свій домен,
  вона потрібна для сканера) і CSP. Зафіксовані тестом `tests/security.php`.
- **HSTS вимкнений за замовчуванням** — вмикається `'hsts' => true` у `config.local.php`.
  Вмикайте лише коли HTTPS працює на **всьому домені**: заголовок діє на домен цілком і
  памʼятається браузером місяцями, тож помилкою можна покласти сусідній сайт, і швидко це
  не відкотити.

### Чого CSP поки що не закриває

`script-src` містить `'unsafe-inline'`. Це означає: якщо кудись усе-таки вдасться вставити
`<script>`, CSP його **не зупинить**. Причина — у шаблонах вісімнадцять інлайнових `<script>`
і близько двадцяти `onclick`, і сувора політика просто поклала б сайт.

Решта директив при цьому не декоративна й працює навіть так: `base-uri` не дає підмінити
`<base>` і перенаправити всі відносні шляхи на чужий домен, `form-action` не дає вставленій
формі відправити дані назовні, `connect-src` не лишає вкраденому куди поїхати, `object-src`
прибирає цілий клас старих векторів.

Шлях до суворої політики, якщо колись знадобиться: видавати нонс на запит, дописати його
кожному `<script nonce="…">`, перенести `onclick` у слухачі подій — і прибрати `'unsafe-inline'`.
Робота на пів дня й помітний ризик щось непомітно зламати, тож робити її варто окремо, а не
перед переїздом на бойовий сервер.

## Перенос на бойовий сервер: покроково

Розділяємо за природою речей, а не за зручністю:

| Що | Чим переносимо | Чому саме так |
|---|---|---|
| Код | **git** (GitHub → cPanel Git Version Control) | оновлюється постійно, має історію, відкочується |
| База | **вручну**, підготовленими запитами | демо-дані сідера в прод не можна |
| Фото з `assets/uploads/` | **Диспетчер файлів або FTP** | вони в `.gitignore` навмисно |

Фото через git не переносимо не тому, що «засмітять», а тому, що це **контент, а не
код**: він народжується на бойовому сервері, коли ви завантажуєте картку товару. Якби
він жив у репозиторії, кожне завантаження фото з адмінки вимагало б коміту, а
розгортання — затирало б те, що завантажили після останнього пуша. `.gitignore` цю межу
вже проводить, і переносити її не варто.

### 1. Файли

1. cPanel → Git Version Control → налаштувати клон (див. розділ вище).
2. **Pull or Deploy → Update from Remote → Deploy HEAD Commit.**
3. Перевірити, що в `public_html/bofu` є `.htaccess` (Диспетчер файлів показує приховані
   файли після Налаштування → «Показувати приховані файли»). Немає — розгортання
   пішло не так, далі йти не можна.

Далі кожне оновлення — це `git push` локально й дві кнопки в cPanel. Більше нічого.

### 2. База

1. cPanel → MySQL Databases → створити **порожню** базу й користувача, дати всі права.
2. Створити на сервері `config.local.php` з цими доступами (див. «Перенос на HostIQ», п. 4).
3. cPanel → Terminal:
   ```bash
   cd ~/public_html/bofu && php bin/cli.php migrate
   ```
   Створить таблиці **без демо-даних**. Важливо зробити це до першого відкриття сайту:
   `App::dbReady()` бачить порожню базу як «перший запуск» і сам запускає сідер із
   демо-товарами й демо-адміністратором.
4. Наповнити довідники своїми запитами (категорії, товари, магазини) або руками
   в адмінці — після кроку 3.

**Якщо демо-дані все-таки з'явились** (сайт відкрили раніше, ніж виконали `migrate`,
і `App::dbReady()` прийняв порожню базу за перший запуск) — чистити треба однією
командою разом із міграцією, інакше між ними лишається вікно, у яке встигає будь-яка
відкрита вкладка чи бот, і демо-дані повертаються:

```bash
cd ~/public_html/bofu && php bin/cli.php wipe НАЗВА_БАЗИ && php bin/cli.php migrate
```

`wipe` видаляє **всі** таблиці бази й вимагає її назву аргументом — не прапорець
`--force`, який дописують не читаючи, а саме назву: її треба свідомо подивитися в
`config.local.php` і надрукувати, і на чужій базі вона не збігається. Без правильної
назви команда нічого не робить.

### 3. Перший адміністратор

Тут єдине неочевидне місце всього переносу. Вхід через Google створює людину
**покупцем** — і правильно робить: інакше будь-хто, хто натиснув «Увійти», ставав би
адміністратором. Але на порожній базі це замикає коло: щоб роздати ролі, треба вже мати
доступ до адмінки.

Розмикається так:

1. Відкрити сайт, **увійти через Google** своєю поштою. Акаунт створиться покупцем.
2. cPanel → Terminal:
   ```bash
   cd ~/public_html/bofu && php bin/cli.php grant-admin ваша@пошта
   ```
3. Перезайти на сайт. Тепер доступна адмінка.

Команда працює лише з консолі — тобто в того, хто має доступ до хостингу. З браузера
підвищити собі права нема як.

### 4. Фото

Скопіювати вміст локальної `assets/uploads/` у `public_html/bofu/assets/uploads/`
через Диспетчер файлів (зручно ZIP-ом: завантажити архів, потім «Видобути»). Права на
теку — 755. Розгортання git ці файли не чіпає: вони не в репозиторії.

### 5. Перевірка

```bash
cd ~/public_html/bofu && php bin/cli.php prod-check
```

Доки не покаже «Готово до бойового сервера» — на сайт нікого не пускаємо. Далі зняти
`seo_noindex` в Налаштуваннях, щоб сайт побачили пошуковики.

## Перевірка готовності: `php bin/cli.php prod-check`

Показує, що заважає пускати на сайт покупців. Нічого не змінює — виправлення завжди рішення
людини: те, що на локальній машині помилка, на тестовому стенді буває навмисним.

Перевіряє: демо-вхід і показ помилок, режим, наявність `config.local.php`, HSTS,
демо-користувачів `@bofu.local` і демо-магазини із сідера, чи лишився **справжній**
адміністратор, координати точок, тестові замовлення, ключ карти, заборону індексації,
права на теки запису і — окремо — чи доїхали всі `.htaccess`.

Код виходу ненульовий, якщо є хоч одне «не можна», тож перевірку можна ставити останнім
кроком розгортання.

Порядок дій перед запуском:

1. `php bin/cli.php prod-check` на сервері (cPanel → Terminal, або через SSH).
2. Закрити все, що позначене `✗`.
3. Переглянути `!` — це не блокери, але кожен варто прочитати.
4. Повторити, доки не лишиться «Готово до бойового сервера».

## Перенос на HostIQ (коли буде готово)

1. Експортуйте базу: `docker exec bofu-mysql mysqldump -ubofu -pbofu_secret bofu > dump.sql`
2. У cPanel створіть базу MySQL і імпортуйте dump.sql через phpMyAdmin.
3. Скопіюйте файли проєкту в `public_html` (FTP або File Manager).
4. Створіть `config.local.php` з доступами до бази хостингу:
   ```php
   <?php return ['db' => ['host' => 'localhost', 'port' => 3306,
     'database' => 'xxx_bofu', 'username' => 'xxx_user', 'password' => '...']];
   ```
   Демо-вхід тут не вмикайте — за замовчуванням він вимкнений, і так і має лишитися.
5. Увімкніть SSL (безкоштовний у HostIQ) — запрацюють Web Push і Google OAuth.
6. Перевірте, що `https://ваш-домен/config.php`, `/storage/`, `/app/` віддають 403 —
   якщо ні, у хостингу вимкнений `AllowOverride` і `.htaccess` не діють.
7. Схему бази оновлювати не треба: `App::dbReady()` викликає `Schema::upgrade()` на
   кожному запиті, тож перше ж відкриття сайту доводить базу до поточної версії.
8. Карту точок продажу увімкніть окремо — див. розділ нижче.

## Оновлення сайту через cPanel → Git Version Control

Замість заливати файли по FTP щоразу: cPanel тримає власний клон репозиторію,
забирає з GitHub нові коміти й розкладає їх у теку сайту. Що саме розкладати —
описано в `.cpanel.yml` у корені проєкту.

### Налаштування (один раз)

1. **cPanel → Git Version Control → Create.**
   - *Clone a Repository*: увімкнути.
   - *Clone URL*: `https://github.com/shevulkin/bofu.git`
     (якщо репозиторій приватний — спершу cPanel → SSH Access → створити ключ і
     додати його публічну частину в GitHub як Deploy key, а URL брати `git@`).
   - *Repository Path*: `/home/ВАШ_КОРИСТУВАЧ/repositories/bofu`

   **Не всередині `public_html`.** Клон містить теку `.git` — це вся історія
   проєкту, включно з тим, що колись із файлів видалили. У `public_html` вона
   стала б доступною з інтернету. Кореневий `.htaccess` таке звернення відбиває,
   але покладатись на це як на єдиний захист не варто: `.htaccess` не діє, якщо
   на хостингу обмежений `AllowOverride`.

2. **Перевірити, що гілка `main` вибрана** — розгортається HEAD саме тієї гілки,
   що зараз checked out.

3. Створити на сервері `config.local.php` (див. «Перенос на HostIQ», п. 4).
   Він **не в репозиторії** й розгортанням не переписується — у цьому й задум.

### Оновлення (щоразу)

1. Локально: `git push`.
2. cPanel → Git Version Control → **Manage** біля `bofu` → вкладка **Pull or Deploy**.
3. **Update from Remote** — забрати нові коміти з GitHub.
4. **Deploy HEAD Commit** — розкласти їх у `public_html/bofu`.
5. Відкрити сайт. Схема бази оновиться сама (`Schema::upgrade()` на першому ж запиті).

### Що робить `.cpanel.yml`

Копіює вміст репозиторію в `$HOME/public_html/bofu` через `rsync`, пропускаючи
`.git`, `.gitignore`, `tests/` і `docker-compose.yml`, і виставляє права на теки,
у які пише сам сайт.

Два рішення там варті пояснення, бо обидва — граблі, на які легко стати:

- **`rsync`, а не `cp -R *`.** Зірочка не бачить файлів, що починаються з крапки.
  У проєкті на них тримається все: кореневий `.htaccess` дає примусовий HTTPS і
  маршрутизацію через `index.php`, а `app/.htaccess`, `bin/.htaccess`,
  `storage/.htaccess`, `assets/uploads/.htaccess` закривають доступ до коду,
  логів і завантажених файлів. Розгортання зірочкою дало б сайт, який не
  маршрутизується і водночас віддає власний код. Документація cPanel окремо
  застерігає від зірочки — під неї потрапляє й `.git`.
- **Без `--delete`.** Він прибирав би з сервера файли, яких уже немає в
  репозиторії. Але поруч лежать завантажені фото товарів, яких у git не було
  ніколи, і помилка в одному рядку виключень коштувала б їх усіх. Стара копія
  файлу — проблема, яку видно й можна виправити; стерті фото — ні. Якщо колись
  знадобиться прибирати старі файли, робіть це руками у Диспетчері файлів.

### Якщо розгортання не спрацювало

- **«dirty working tree»** — у клоні на сервері хтось правив файли руками. cPanel
  відмовляється розгортати поверх правок, щоб їх не втратити. Або приберіть
  правки (Git Version Control покаже, які), або переносьте їх у репозиторій.
- **rsync not found** — рідко, але буває. Замініть у `.cpanel.yml` рядок rsync на
  `/bin/cp -R . $DEPLOYPATH/` (крапка, а не зірочка — вона бачить dot-файли),
  і додайте окремим рядком `/bin/rm -rf $DEPLOYPATH/.git`.
- **Файли лягли в `public_html/bofu/bofu`** — загубилась скісна риска в `./` або
  в `$DEPLOYPATH/`. Для rsync `./` означає «вміст цієї теки», а `.` — «цю теку».
- Сайт відкривається, але сторінки 404 — не доїхав кореневий `.htaccess`
  (та сама історія із зірочкою) або на хостингу вимкнений `AllowOverride`.
- **`File not found` на файл, який точно лежить на місці** — права на саму теку
  сайту. `public_html` належить користувачу, але групі `nobody`, і саме через
  групу до нього дістається веб-сервер; підтеки ж створюються з групою
  користувача. Якщо на теці сайту стоїть `0700` або `0750`, сервер не може в неї
  увійти — і повідомляє про це як про відсутній файл, хоча всередині все справне.
  Перевірити весь ланцюжок:
  ```bash
  ls -ld ~/public_html ~/public_html/bofu ~/public_html/bofu/index.php
  ```
  У теки сайту має бути `drwxr-xr-x`. Якщо ні:
  ```bash
  chmod 755 ~/public_html/bofu
  ```
  Звідки береться `0700`: `rsync -a` переносить права джерела, зокрема й на теку
  призначення, а клон, який cPanel створює в `repositories/`, має саме `0700`.
  Тому в `.cpanel.yml` `chmod` стоїть **після** rsync, а не до — інакше сайт лягав
  би рівно після кожного успішного розгортання, і виглядало б це так, ніби
  «деплой щось зламав».
- `$HOME` не розкрився — впишіть шлях повністю: `/home/ВАШ_КОРИСТУВАЧ/public_html/bofu`.
  Ім'я користувача видно у cPanel угорі праворуч і в шляхах Диспетчера файлів.

### Перед першим розгортанням у прод

Схема бази створиться сама, але **демо-дані з локальної бази переносити не можна**.
Сідер заводить трьох користувачів `@bofu.local` — один із них адміністратор, — а
також приклади товарів, категорій, магазинів і замовлень. На бойовому сайті це
означало б чужий адмінський обліковий запис і вітрину з вигаданим товаром.

Порядок для чистого старту:

1. На хостингу створити **порожню** базу й вписати її в `config.local.php`.
2. Відкрити сайт. `App::dbReady()` побачить порожню базу, створить таблиці й
   запустить сідер — тобто демо-дані зʼявляться знову, тепер уже на проді.
3. Увійти через Google своїм акаунтом (він отримає роль адміністратора, якщо в
   базі ще немає інших), після чого **видалити демо-користувачів** в адмінці →
   Користувачі, а демо-товари, категорії та магазини замінити справжніми.

Якщо ж переносите локальну базу дампом (варіант із «Перенос на HostIQ», п. 1–2),
те саме прибирання зробіть **до** експорту або одразу після імпорту. Заразом
перевірте, що `demo_login` у `config.local.php` не увімкнений: цей рядок дає
адмінські права одним кліком без пароля.

## Карта точок продажу

Карта показується у двох місцях: при виборі самовивозу в оформленні та на сторінці
«Де нас знайти» (`/stores`). Обидва працюють і без неї — тоді покупець бачить адресу
з кнопкою «прокласти маршрут», і сторінки нічого не втрачають, крім самої карти.
Тому вмикати її можна коли завгодно, а не «перед запуском».

Google згадується рівно в одному файлі — `assets/js/map.js`. Зміна постачальника
карт (той самий OpenStreetMap, якщо не хочеться прив'язувати картку) коштує його
одного: решта — координати, поле в адмінці, сторінки — від постачальника не залежить.

### Що куди їде

| | Де живе | Їде з git |
|---|---|---|
| Код карти, сторінки, поля | файли | так |
| Стовпці `stores.lat` / `lng` | схема | так (створяться самі, п. 7 вище) |
| Ключ Google Maps | таблиця `settings` | **ні** — вписати в адмінці на сервері |
| Координати магазинів | таблиця `stores` | **ні** — заповнити в адмінці на сервері |

Ключ навмисно не у файлах: у git він не має опинитись ніколи. Якщо базу переносили
дампом (п. 1–2), то і ключ, і координати приїдуть разом із нею.

### Ключ

1. [Google Cloud Console](https://console.cloud.google.com/google/maps-apis/credentials) →
   проєкт із прив'язаним платіжним акаунтом (без картки ключ не видають навіть під
   безкоштовний обсяг).
2. Увімкнути **Maps JavaScript API** — саме його, не Embed і не Static.
3. Створити ключ і одразу обмежити:
   - *Application restrictions* → **Websites**, і **два рядки**:
     ```
     https://ваш-домен/*
     https://www.ваш-домен/*
     ```
     Обидва обов'язково: `https://bofu.ua/*` не покриває `www.bofu.ua` — для Google це
     різні реферери. Для розробки додайте ще `https://localhost/*`.
     Схема завжди `https://`: `.htaccess` примусово редіректить на HTTPS, тож інших
     реферерів не буде.
   - *API restrictions* → **Restrict key** → лише Maps JavaScript API.
4. Поставити **добову квоту** в консолі. Ключ їде у HTML кожної сторінки з картою —
   інакше Google Maps не працює. Обмеження за доменом плюс стеля квоти і є те, що
   робить нульовий рахунок гарантією, а не сподіванням: секретності тут не буває.
5. Вписати ключ: **Адмінка → Налаштування → «Google Maps: ключ»**.

Зміни в обмеженнях застосовуються не миттєво — до кількох хвилин.

### Координати магазинів

**Адмінка → Магазини**, поле «Координати». Три способи, усі три робочі:

- **📍 обрати на карті** — відкриється карта, клацнути по своєму входу, мітку можна
  перетягнути. Кнопка з'являється лише коли заданий ключ.
- Вставити пару чисел із Google Maps: права кнопка по місцю → перший рядок меню.
  Кома як десятковий знак (`50,4501, 30,5234`) теж підійде — саме так її копіює
  система з українською локаллю.
- Вставити посилання на місце — розберемо.

Поруч із заповненим полем є «перевірити →»: воно відкриває цю точку в Google Maps.
Натисніть після заповнення — пара чисел виглядає правдоподібно й тоді, коли вказує
на сусідній квартал, і оком це ловиться лише на самій карті.

Точка без координат лишається в списку самовивозу, але не має мітки на карті.
Пошуку адреси у вікні вибору немає навмисно: він живе в окремому API Google (Places)
з окремою оплатою, тобто коштував би грошей при кожному відкритті — заради дії, яку
роблять раз на магазин.

### Якщо карта не з'явилась

F12 → Console. Google називає причину прямо:

| Помилка | Що робити |
|---|---|
| `RefererNotAllowedMapError` | домен не доданий у ключ, або зміни ще не поширились |
| `ApiNotActivatedMapError` | не увімкнено Maps JavaScript API |
| `BillingNotEnabledMapError` | не прив'язано платіжний акаунт |
| `InvalidKeyMapError` | ключ скопійований з помилкою |

Якщо помилок немає, а карти теж — перевірте, чи є хоч в одного **активного** магазину
координати: без них блок карти не виводиться зовсім.
